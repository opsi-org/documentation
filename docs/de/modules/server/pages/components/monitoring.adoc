[[server-components-opsiconfd-check-monitoring]]
= Health-Check & Monitoring

Opsi bietet einen Health-Check an, der den Betriebszustand des OPSI-Servers überprüft. Dieser Health-Check kann zum Beispiel über die Weboberfläche des OPSI-Servers aufgerufen werden. Der Health-Check prüft die Funktionalität und gibt eine Übersicht über den Status der verschiedenen Komponenten des OPSI-Servers.

Der Health-Check kann in ein Monitoring-System integriert werden, um dort den Status des OPSI-Servers zu überwachen.

[[server-components-opsiconfd-health-check]]
== Health-Check

Der `opsiconfd` stellt einen Health-Check bereit, der verschiedene Einstellungen und Versionen von OPSI-Komponenten überprüfen und damit Hinweise auf eventuelle Probleme geben kann. Der Health-Check kann auf unterschiedliche Weise gestartet werden. Alle Varianten beziehen ihre Daten vom API-Call `service_healthCheck`. Die OPSI-API liefert die Daten im JSON-Format zurück. Eine solche JSON-Datei ist besonders bei Support-Anfragen nützlich.

Eine Möglichkeit einen Health-Check zu starten, ist über die Admin-Seite, Reiter _RPC-Interface_ (siehe Abschnitt xref:server:components/opsiconfd.adoc#server-components-opsiconfd-admin-page-rpc-interface[RPC Interface]). Auch das OPSI-WebGUI bietet schnellen Zugriff auf den xref:gui:webgui/userguide-system.adoc#opsi-manual-opsiwebgui-system-healthcheck[Health-Check]. Auf der Kommandozeile erfolgt der Aufruf über den Befehl `opsiconfd health-check`. Über den Parameter `--help` blenden Sie eine Onlinehilfe ein; `opsiconfd health-check --documentation` gibt eine Beschreibung aller Checks aus. Ohne weitere Optionen läuft der Check einmal durch und schreibt seine Ergebnisse nach `stdout`.

`opsiconfd health-check --list` gibt alle verfügbaren Checks mit Namen und ID aus. Ein bestimmter Check kann mit `opsiconfd health-check --checks <ID>` ausgeführt werden. Checks die nicht ausgeführt werden sollen, können mit `--skip-checks <ID>` übersprungen werden.
Die `checks` und `skip-checks` können auch in der `/etc/opsi/opsiconfd.conf` oder über Umgebungsvariablen (OPSICONFD_CHECKS bzw. OPSICONFD_SKIP_CHECKS) konfiguriert werden.

.Den Health-Check können Sie im Terminal starten.
image::server:opsi-health-check.png["Den Health-Check können Sie im Terminal starten.", width=800, pdfwidth=80%]

TIP: Der Health-Check kann auch mit dem Kommandozeilentool `opsi-cli` aufgerufen werden (siehe Abschnitt xref:server:components/commandline.adoc#server-components-opsi-cli-commands-support[*opsi-cli support*]). Einen schnellen Zugriff auf ein Terminal auf dem OPSI-Server bietet die Admin-Seite über den Reiter _Terminal_ (siehe Abschnitt xref:server:components/opsiconfd.adoc#server-components-opsiconfd-admin-page-terminal[Opsiconfd Terminal]).


=== Ausgabeformate

Der Health-Check kann folgende Ausgaben produzieren:

- cli (default): Für die Kommandozeile angepasste Ausgabe.
- json: Ausgabe im JSON-Format.
- checkmk: Ausgabe, sodass sie von Checkmk verarbeitet werden kann.
- zabbix: Ausgabe, sodass sie von Zabbix verarbeitet werden kann.
- nagios: Ausgabe, sodass sie von Nagios verarbeitet werden kann.

Die Ausgabeformate können über den Parameter `--format` gesteuert werden.

[source,console]
----
opsiconfd health-check --format json
----

=== Caching

Die Ergebnisse der einzelnen Checks werden in Redis gespeichert und bleiben 24 Stunden gültig. Verschiedene Funktionen wie zum Beispiel das Erstellen eines Backups sorgt dafür, dass der Cache für den Backup-Check geleert wird.

Wird der Health Check mit dem Parameter `--clear-cache` aufgerufen, wird der Cache geleert und alle Checks werden erneut ausgeführt.
Auch der API Methode `service_healthCheck` kann der Parameter `clear_cache` übergeben werden, um den Cache zu leeren.

[source,json]
----
{
  "method": "service_healthCheck",
  "params": {
	"clear_cache": true
  }
}
----


[[server-components-opsiconfd-monitoring]]
== Monitoring

Der Health-Check kann in ein Monitoring-System integriert werden, um eine kontinuierliche Überwachung der Systemgesundheit und -leistung zu ermöglichen. Dabei lässt sich der Health-Check über das Monitoring-System regelmäßig aufrufen. Die Resultate können für verschiedene Zwecke ausgewertet werden, etwa für Alarme, Protokolle oder für die Automatisierung von Wartungsprozessen.

[[server-components-opsiconfd-checkmk]]
=== Checkmk

Um die Ergebnisse des Health-Checks in Checkmk zu nutzen, werden ein oder mehrere "local checks" eingerichtet.
Checkmk ist ein flexibles und erweiterbares Monitoring-Tool, das speziell für die Überwachung von IT-Infrastrukturen entwickelt wurde.
Durch die Integration von Health-Check-Daten können Administratoren sicherstellen, dass die Systeme stets im optimalen Zustand sind und eventuelle Probleme frühzeitig erkannt werden.

Der opsiconfd bringt ein Template-Shell-Skript mit, das die Ausgabe des Health-Checks in das Checkmk-Format umwandelt.
Dieses Skript ist in der Datei opsi_checkmk enthalten, die unter /usr/share/opsiconfd zu finden ist.
Die Datei kann als "local check" in Checkmk eingebunden werden, um die Health-Check-Daten regelmäßig zu erheben und auszuwerten.

Für die Integration kopiert man das Skript nach /usr/lib/check_mk_agent/local/<cache-time>, wobei <cache-time> für das Cache-Intervall steht, in dem die Ergebnisse aktualisiert werden.
Nach dem Kopieren muss das Skript ausführbar gemacht werden, um korrekt zu arbeiten.

Hier ein Beispiel, wie man das Skript für regelmäßige Abfragen einbindet:

[source,console]
----
cp /usr/share/opsiconfd/opsi_checkmk /usr/lib/check_mk_agent/local/600/opsi_check
chmod +x /usr/lib/check_mk_agent/local/600/opsi_check
----

In diesem Beispiel wird der Health-Check alle 600 Sekunden (10 Minuten) durch den Checkmk-Dienst aufgerufen. Die Zeitspanne kann je nach Bedarf angepasst werden, um eine feinere oder gröbere Granularität bei der Datensammlung zu erreichen.

Für eine detaillierte Beschreibung der Checkmk local checks und ihrer Konfiguration können Sie die offizielle Checkmk-Dokumentation hier einsehen: https://docs.checkmk.com/latest/de/localchecks.html.

Mit den Parametern --checks oder --skip-checks kann das Verhalten des Health-Checks weiter angepasst werden. Beispielsweise können bestimmte Checks aktiviert oder deaktiviert werden, um maßgeschneiderte Überwachungsstrategien zu realisieren (siehe Abschnitt xref:server:components/monitoring.adoc#server-components-opsiconfd-health-check[Health-Check]).

=== Nagios / Icinga

Um die Ergebnisse des Health-Checks in Nagios oder Icinga zu integrieren, kann das Skript `/usr/share/opsiconfd/opsi_nagios` verwendet werden, das die Ausgabe des Health-Checks in ein für Nagios/Icinga lesbares Format umwandelt.
Das Skript wird hierzu in das Verzeichnis `/usr/lib/nagios/plugins/` kopiert und ausführbar gemacht.

[source,console]
----
cp /usr/share/opsiconfd/opsi_nagios /usr/lib/nagios/plugins/opsi_check
chmod +x /usr/lib/nagios/plugins/opsi_check
----

Dem Check-Script kann ein Parameter übergeben werden, um den gewünschten Health-Check auszuführen. Die Parameter entsprechen den IDs der OPSI-Checks. Zum Beispiel:
[source,console]
----
opsi_check mysql
----

Die Liste der verfügbaren Checks kann mit dem Befehl `opsiconfd health-check --list` abgerufen werden. Um detaillierte Informationen zu einem bestimmten Check zu erhalten, verwenden Sie `opsiconfd health-check --docs`.

In der Nagios/Icinga-Konfiguration wird dann ein Kommando definiert, das dieses Skript aufruft. Hier ein Beispiel für eine Icinga2-Kommando-Definition:

image::opsi-icinga2-command.png["Icinga2 Kommando-Definition", width=500]


Anschließend wird ein Service definiert, der dieses Kommando nutzt. Hier ein Beispiel für eine Service-Vorlagen-Definition:

image::opsi-icinga2-service.png["Icinga2 Service-Definition", width=500]

Dann wird der Service einem Host zugewiesen, um die Health-Check-Daten zu überwachen. Hier ein Beispiel für eine Host-Definition:

image::opsi-icinga2-host.png["Icinga2 Host-Definition", width=500]

Im letzten Schritt werden die Konfigurationen ausgerollt, um die Änderungen zu aktivieren.

IMPORTANT: Der Benutzer, unter dem der Icinga2-Dienst läuft, benötigt Lesezugriff auf die Datei `/etc/opsi/opsiconfd.conf`, um die Konfiguration des Health-Checks zu lesen. Dies kann durch Hinzufügen des Benutzers zur Gruppe `opsiadmin` erfolgen.

Weitere Informationen zu Icinga2 in der Dokumentation: https://icinga.com/docs/icinga-2/latest/doc/01-about/


[[server-components-opsiconfd-zabbix]]
=== Zabbix

Um die Ergebnisse des Health-Checks in Zabbix zu integrieren, können sogenannte `UserParameter` verwendet werden.
Der opsiconfd stellt dafür das Shell-Skript `/usr/share/opsiconfd/opsi_zabbix` bereit, das die Einbindung vereinfacht.

Ein Beispiel für einen UserParameter, der den Redis-Check ausführt:

[source,ini]
----
UserParameter=opsi.redis,/usr/share/opsiconfd/opsi_zabbix redis
----

Um herauszufinden, welche Checks verfügbar sind, verwenden Sie den Befehl `opsiconfd health-check --list --detailed`.
Detaillierte Informationen zu einem bestimmten Check erhalten Sie mit `opsiconfd health-check --docs`.

In der Zabbix-Konfiguration legen Sie anschließend ein Item vom Typ `Text` an, das diesen UserParameter verwendet.
Wählen Sie als Typ `Zabbix Agent` und als Schlüssel den Namen des UserParameters, hier also `opsi.redis`.
Das Aktualisierungsintervall kann flexibel gewählt werden, zum Beispiel 60 Sekunden, da die Ergebnisse des Health-Checks von **opsiconfd** in Redis zwischengespeichert werden und somit keine hohe Systemlast entsteht.
Setzen Sie den Timeout für das Item auf 10 Sekunden.

Für die Alarmierung richten Sie Trigger ein, die den Text des Items auswerten.
Dabei sollte geprüft werden, ob das Ergebnis mit `OK`, `WARNING` oder `CRITICAL` beginnt, um den Status korrekt zu erkennen.

[[server-components-opsiconfd-monitoring-downtimes]]
== Monitoring-Integration: Downtimes über OPSI setzen und entfernen

`opsiconfd` kann Downtimes für Hosts und Services in einem Monitoring-System anlegen und wieder entfernen. Das Feature ist Teil der xref:opsi-modules:modules.adoc[OPSI-Erweiterung] https://opsi.org/de/product/extensions/#monitoring-connector[Monitoring Connector]. Zunächst wird nur Checkmk unterstützt; weitere Systeme sind geplant. Wenn Sie an der Unterstützung weiterer Monitoring-Systeme interessiert sind, nehmen Sie gerne Kontakt mit uns auf.

So lassen sich per opsi-script Downtimes für einzelne Services oder den gesamten Host setzen, um Alarme während der Installation von Updates zu vermeiden.

=== Funktionen

* *Neue RPC-Methoden:* `monitoring_setDowntime`, `monitoring_removeDowntime`, `monitoring_getDowntimes`, `monitoring_getInfo` und `monitoring_checkConnection`.
* *Nutzung durch OPSI-Clients:* Clients können per opsi-script Downtimes für sich selbst setzen und entfernen.
* *Automatisches Ende:* Beim Setzen einer Downtime muss eine Dauer angegeben werden (maximal 14400 Sekunden; der Höchstwert ist konfigurierbar). Bricht ein Skript ab, endet die Downtime automatisch, und das Problem wird anschließend wieder im Monitoring angezeigt.
* *Sicherheit:* Clients dürfen ausschließlich Downtimes für ihren eigenen Host verwalten. Entfernt werden nur Downtimes, die OPSI selbst angelegt hat (erkennbar am Kommentar-Präfix).
* *Hostname im Monitoring:* Standardmäßig wird die Client-ID (FQDN) verwendet. Über die Konfiguration `monitoring.host_name` lässt sich pro Host ein abweichender Name festlegen; diese Konfiguration dürfen nur Administratoren ändern.

=== Einrichtung

Aktivierung und Zugangsdaten werden in `/etc/opsi/backends/monitoring.conf` konfiguriert. Voraussetzung ist das Modul `monitoring` (siehe xref:opsi-modules:modules.adoc[OPSI-Erweiterungen]). Bestehende `acl.conf`-Dateien werden beim Setup automatisch um die neuen Einträge ergänzt.

=== Beispiel: Verwendung in einem opsi-script-Produkt

Das folgende Beispiel setzt eine Downtime für den gesamten Host und für den Service `nginx` und entfernt sie wieder. Die Aufrufe erfolgen über `OpsiServiceCall`-Sektionen.

[source,opsiscript]
----
comment "Set monitoring downtime for host"
DefStringList $ServiceResult$
Set $ServiceResult$ = getReturnListFromSection('OpsiServiceCall_set_host_downtime')
DefVar $downtimeIds$ = jsonAsObjectGetValueByKey(takeString(0, $ServiceResult$), "downtimeIds")
if ($downtimeIds$ = "")
	LogError "Failed to set monitoring downtime"
	isFatalError "Failed to set monitoring downtime"
endif

...

comment "Remove monitoring downtime for host"
OpsiServiceCall_remove_host_downtime

...

comment "Set monitoring downtime for service nginx"
OpsiServiceCall_set_nginx_downtime

...

comment "Remove monitoring downtime for service nginx"
OpsiServiceCall_remove_nginx_downtime

...

[OpsiServiceCall_set_host_downtime]
; Set a downtime for the entire host, not just specific services.
"method":"monitoring_setDowntime"
"params":[
	'1800',
	'"System update"',
]

[OpsiServiceCall_remove_host_downtime]
; Only downtimes created by OPSI are removed.
"method":"monitoring_removeDowntime"
"params":[
]

[OpsiServiceCall_set_nginx_downtime]
; Set a downtime for the service nginx only.
"method":"monitoring_setDowntime"
"params":[
	'60',
	'"Update nginx"',
	'["nginx"]',
]

[OpsiServiceCall_remove_nginx_downtime]
"method":"monitoring_removeDowntime"
"params":[
	'null',
	'["nginx"]',
]
----

Der erste Parameter von `monitoring_setDowntime` ist die Dauer in Sekunden, der zweite der Kommentar und der optionale dritte eine Liste von Services. Ohne Service-Liste gilt die Downtime für den gesamten Host.

== Downtime

Für bestimmte Health-Checks kann eine Downtime festgelegt werden, um temporäre Ausfälle oder Wartungsperioden zu berücksichtigen, ohne dass falsche Alarme ausgelöst werden. Die Downtime kann entweder für einen spezifischen Check oder für das gesamte Monitoring-System gesetzt werden. Dies ist besonders nützlich, wenn geplante Wartungsmaßnahmen oder Updates durchgeführt werden, die zu einem vorübergehenden Verlust der Systemverfügbarkeit führen.

Die Downtime für einen Health-Check kann über folgende Konfigurationsparameter festgelegt werden:

  - opsi.check.enabled (Standard: true) – Aktiviert oder deaktiviert den Health-Check. Wenn false, wird der Check nicht ausgeführt.

  - opsi.check.downtime.start (Standard: null) – Startzeit der Downtime im ISO-8601-Format (z.B. 2025-03-25T08:00:00).

  - opsi.check.downtime.end (Standard: null) – Endzeit der Downtime im ISO-8601-Format. Das Ende der Downtime legt fest, wann der Check nach der festgelegten Pause wieder aktiviert wird.

Diese Parameter können in der Client-Übersicht im opsi-configed gesetzt werden. Im Client-Details-Bereich auf der rechten Seite finden Sie eine Anzeige mit dem Titel Health-Check active und einem Zahnradsymbol. Über dieses Zahnradsymbol können Sie die Downtime-Parameter konfigurieren.
